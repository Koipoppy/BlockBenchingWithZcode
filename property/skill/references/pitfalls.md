# 坑与修复的完整记录（霸王花盆栽，2026-09-24）

一次"MC 风格花盆 + PvZ 霸王花"建模中实际踩到的每个坑：症状、定位过程、根因、修复，
以及当时为什么会被坑。按发现顺序排列。

## 1. 背面剔除用错了坐标系 —— 花盆下半凭空消失

**症状**：3/4 视角的预览里，花盆底座只剩一个楔形，边缘斜切、还拖着一条尖角；
正面（正对 -Z）看却完全正常。模型 JSON 本身查不出任何问题。

**定位**（这个流程值得记住）：

1. 把可疑件（花盆底座 6 个面）**单独**渲染 —— 是一个完整的立方体。几何、UV、光栅化都没问题
   ⇒ 是遮挡或剔除问题
2. 对缺失区域取一个像素，遍历全部三角形算屏幕空间重心坐标：覆盖该像素的**只有一个**四边形，
   就是那个"消失"的面本身，depth 19.0，没有任何东西挡它 ⇒ 它被**错误剔除**了
3. 读剔除那行代码：`dot(normal, eye - view_pts.mean())` —— `view_pts` 是 `project()`
   返回的**相机系**坐标，`eye` 却是**世界系**的。两个坐标系一相减，得到的是垃圾向量，
   于是该剔的没剔、不该剔的剔了

**修复**：剔除测试两侧必须同一坐标系——用世界系面心：
`dot(normal, eye - verts.mean(axis=0))`。

**教训**：z-buffer 让绘制顺序无关紧要，容易让人忘了剔除测试仍然是一段几何判断，
它的两个操作数必须同系。凡是"部分面消失、边缘斜切、拖着尖角"的渲染，
第一嫌疑就是剔除/投影的坐标系不一致。

## 2. 头灯式光照把白牙画成灰

**症状**：嘴里的白牙、脸上的眼白渲染出来是中灰色，整张贴图的明暗设计全部失效；
从某些角度看整个模型像蒙了一层灰。

**根因**：渲染器用了"随相机方向的头灯 + 环境项"。像素画的明暗**全部在贴图里**
（白牙 246,243,229 对近黑的口腔 58,14,26），任何把所有面拉向同一亮度的光照都会毁掉这层对比。
另外最初的环境项太低（0.52），朝 -Z 的面（嘴的开口方向）全部落到环境亮度。

**修复**：改用 MC 方块自己的面光照——顶 1.0 / 南北 0.8 / 东西 0.6 / 底 0.5，
倾斜面按法线分量平方加权混合（45° 斜面自然得到 0.8 一类的中间值）。
这样正交面精确落在游戏里的数值上，白色保持白色，深度感由**贴图**负责。

**教训**：做像素画渲染器时，光照的作用是"复现游戏的面系数"，不是"重新打光"。

## 3. 花瓣环半径小于被环绕体 —— 一团碎纸

**症状**：8 片花瓣围在花头四周，渲染出来不是花，是贴在方块侧面的一堆碎红色纸片。

**根因**：花瓣环起始半径 2，花头半宽 5——花瓣内段(半径 2→5)整个插在头部体积里，
只有露出头外的部分可见，且各片互相穿插。

**修复**：把整圈花瓣**下移到花头下方**（y 14-15，花头从 16 开始），半径从 2.5 起步、
长 6——起点藏在头底之下本来就不可见，露出的部分从轮廓外展开；再垫一圈绿色萼片
（更低、更平、相位错开 22.5°）补层次。

**教训**：环绕件的"起始半径"是相对**被环绕体的轮廓**而言的，不是相对轴心。
拿不准就把环放到被环绕体的高度范围之外。

## 4. 大长方体读作箱子

**症状**：花头是 10×8×10 的方块开一个方口，渲染出来像"开了一个门的箱子"，
不像生物的头。

**修复**：把 skull 拆成两层——下层 10×8，上层 8×6 四边各收 1 格叠上去，
脸（眼睛）画在收分后的上块正面。一眼从"箱子"变成"头"。
这是 MC 模型做圆润的标准手法：轮廓来自 1 格步进的阶梯，不来自圆滑曲面。

## 5. 亚像素特征：0.4 格的嘴缝是不存在的

**症状**：最初嘴的上下牙间隙 0.4 单位、牙缝 0.45 单位，渲染出来要么全糊要么是一条白带。

**修复**：所有"缝"做到 ≥1 格。嘴张开总高 4 格：下牙 1.5、暗带 1、上牙 1.5；
齿列之间留 1 格宽的暗缝，露出后面的喉咙和舌头——牙齿咬合感来自这些暗缝，不来自上下牙之间的缝。

**教训**：在 16px/block 的世界里先问"这是几像素"。小于 1 的尺寸要么放大，
要么换成"两个实体之间的暗缝"这种 1px 就能表达的结构。

## 6. UV 约定抄错来源 —— 渐变在南北面画反

**症状**（设计期发现，未进渲染）：花瓣"根暗尖亮"的渐变如果在南北面镜像，
半数花瓣的亮尖会朝向花头。

**根因**：minecraft-animation skill 的 Blender 导入器用"north/south 翻 u"的
box-net 约定（那是**它自己**的顶点排布约定，实测过与它的渲染一致）；Blockbench 本体
的显式 uv 却是 WYSIWYG（见 bbmodel-format.md §1-2）。两套都对，但**互不通用**，
照搬会把方向性渐变画反。对称画法（贴图沿中线左右对称）能掩盖差异，
方向性渐变（花瓣、叶片）则会暴露它。

**修复**：以 Blockbench 源码为准；up/down 面从相反方向看同一矩形的件
（沿 Z 放的叶片），干脆给两个矩形（`leaf_z_up` / `leaf_z_dn`），不做运行时翻转。

**教训**：约定类知识必须注明出处和适用范围。"某个 Blender 导入器验证过的表"
不等于"Blockbench 的约定"。

## 7. outliner 写平 —— 多个根 + 悬空引用

**症状**（结构期，由 validator 抓到）：把所有组平铺在 outliner 顶层、用 uuid 互相指，
Blockbench 会读成几个不相关的根，元素引用悬空。

**修复**：嵌套组**内联为对象**，只有元素用 uuid 字符串引用；
每个元素必须被 outliner 引用一次（validator 的"孤儿元素"检查）。
生成脚本里用 `walk(node)` 递归：先收集 `cubes` 的 uuid，再递归 `children`。

## 8. 读 Blockbench 源码：asar 与压缩 bundle

**症状**：直接 `grep` `resources/app.asar` 得到的是 vite 压缩后的单行 bundle，
变量名全是 `Ui`、`c`、`s`，读不了；而且 asar 头部按错误的偏移解析会直接 JSONDecodeError。

**修复**：

- asar 头：`@0=4`、`@4=headerSize`、`@8=headerSize-4`、`@12=jsonLen`、JSON 在 `@16`，
  文件数据从 `8+headerSize` 开始
- 要读的是 `dist/bundle.js.map`（约 19MB）：`sources[]` 是原始路径、
  `sourcesContent[]` 是未压缩源码，按路径下标取
- 只需要 5 个文件：`three_custom.js`（顶点序）、`cube.js`（updateUV / box-uv net）、
  `preview.ts`（默认相机）、`generic.ts`（free 格式）、`io/format.ts`（默认值）

**教训**：Electron 应用的"文档"经常就是它自己的 source map。格式问题先去那里找，
比试错快得多。

## 9. 环境类小坑（各耗掉一次构建）

- **Git Bash 的 `/tmp` 对原生 Windows Python 不成立**：内联脚本里写
  `open('/tmp/x.png','w')` 报 FileNotFoundError，但命令行参数里的 `/tmp/x.png`
  又会被 MSYS 改写成功。统一用 `os.environ['TEMP']` 或显式 `C:/` 路径
- **参考图全网不可达**：fandom 404/超时、萌娘 404、百度百科 403、必应跳 cn 站无结果。
  美术参考要么按名称+题材惯例自己设计并**显式声明假设**，要么一开始就找用户要图——
  不要把回合烧在重试 URL 上
- **asar 解析别照抄记忆里的偏移**：第一版把 jsonLen 读在 @8，直接把文件数据当 JSON 解析

## 10. 渲染器实现细节（各耗掉一次构建，记录备查）

- 三角形顶点是 `(x, y, inv_w)` 三元组，解包时 `x0, y0 = points[0]` 会崩——用 `points[0][:2]`
- 阴影遮罩和深度填充共用一个光栅函数时，`window`/`depth` 这类参数在遮罩路径里是 None，
  判空要在使用之前，不能先 `mask[...]` 再判
- 透视校正插值：屏幕空间重心坐标 λ 配每顶点 `1/w`，
  属性 = `Σ(λᵢ·aᵢ/wᵢ) / Σ(λᵢ/wᵢ)`；深度测试直接用插值出的 `1/w`（越大越近）
- 投影时把 `depth = -z_view` clamp 到 `1e-6` 防除零，但别让任何顶点真的落到相机背后
  ——那会把整个三角形拉成横跨全屏的垃圾

## 11. 逐面 UV 角的三元写反 —— 每个面的贴图 180° 旋转

**症状**：预览图里每个面的贴图都是"上下颠倒 + 左右镜像"。**噪点/迷彩贴图完全看不出来**（噪点
转 180° 还是噪点），只有方向性贴图能看出来——肌肉苦力怕的脸（眼在上、嘴在下）一眼就穿帮。
`bbmodel` 工程本身从未受影响，只有离线预览 PNG 错。

**根因**：渲染器把 uv 矩形四角配到面四个顶点时，三元表达式写反了：

```python
((u1 if cx else u2), (v1 if cy else v2))   # ✗ v0 拿到右下角 = 整面转 180°
((u2 if cx else u1), (v2 if cy else v1))   # ✓ v0 拿到左上角 (u1,v1)
```

两者只差一个 `if/else` 的取向，行文上几乎读不出差别——**源码推导是对的，代码写反了**，
而当时用于检查的模型（花盆、盆栽）贴图都是近似对称/噪点，没暴露出来。

**怎么定论**（这套办法值得复用）：

1. 用同一模型、同一相机，把两种映射各渲染一张，直接看图——苦力怕的脸一张正立、一张倒立；
2. 外部参照：`muscle_creeper_blockbench.png` 是 Blockbench GUI 的实机截屏，脸部朝向可作为真值；
3. 更普适的真值：**香草皮肤布局的脸本来就该正立**（`64×32` 皮肤里头部正面在 `(8,8)-(16,16)`），
   任何让脸倒过来的映射都是错的。

**教训**：UV 方向**不要用噪点贴图验证**。用一个"脸/字母/箭头"测试贴图，或者在模型上找一块
有明确上下之分的贴图；把这张方向性贴图作为预览器的固定自检用例。

## 12. Blockbench 保存过的工程是 5.0 格式 —— 组的旋转会"失效"

**症状**：`ship_in_bottle.bbmodel` 在 Blockbench 里被打开保存过之后，渲染/解析脚本按老办法
从 outliner 读组的 `origin`/`rotation`，结果全部读成缺省值。

**根因**：Blockbench 5.x 保存工程时写 `meta.format_version = "5.0"`，把组整个搬到顶层
`groups` 数组（name/origin/rotation/children 都在那里），`outliner` 里的节点退化成
`{uuid, isOpen, children}` 纯引用；元素还多出 `scope`/`autouv`/`locked` 等字段，数字按整数写。
详见 [bbmodel-format.md §11](bbmodel-format.md)。

**为什么一开始没炸**：组的 `origin` 只是 pivot，**不会平移子元素**（元素的 from/to 是模型空间的
绝对坐标），而那个工程里 7 个组的 `rotation` 全是 0 —— 于是"读不到"和"读到 0"结果一样。
**一旦有旋转组（摆动、倾斜）就会静默渲染错**。

**修复**：解析时两边都读——节点里没有 `origin`/`rotation` 就按 `uuid` 查顶层 `groups` 表。
已落进 `tools/preview_bbmodel.py` 的 `collect_quads`，并用"给 `hull` 组注入 45° 旋转后画面必须变化"
的对照实验验证（4.5 内联组同样对照，作为回归）。

**顺带确认的事**：4.5 → 5.0 重新保存**不改几何**——同一渲染器对两个版本输出逐像素一致
（平均差 0.000）。但生成脚本只会写 4.5，对 Blockbench 保存过的文件重跑脚本会退回 4.5 并丢掉 GUI 修改。
