# 坑与修复的完整记录（霸王花盆栽，2026-09-24）

一次"MC 风格花盆 + PvZ 霸王花"建模中实际踩到的每个坑：症状、定位过程、根因、修复，
以及当时为什么会被坑。按发现顺序排列。

## 1. 背面剔除用错了坐标系 —— 花盆下半凭空消失

**症状**：3/4 视角的预览里，花盆底座只剩一个楔形，边缘斜切、还拖着一条尖角；
正面（正对 -Z）看却完全正常。模型 JSON 本身查不出任何问题。

**定位**（这个流程值得记住）：

1. 把可疑件（花盆底座 6 个面）**单独**渲染 —— 是一个完整的立方体。几何、UV、光栅化都没问题
   ⇒ 是遮挡或剔除问题
2. 对缺失区域取一个像素，遍历全部三角形算屏幕空间重心坐标：覆盖该像素的**只有一个**四边形，
   就是那个"消失"的面本身，depth 19.0，没有任何东西挡它 ⇒ 它被**错误剔除**了
3. 读剔除那行代码：`dot(normal, eye - view_pts.mean())` —— `view_pts` 是 `project()`
   返回的**相机系**坐标，`eye` 却是**世界系**的。两个坐标系一相减，得到的是垃圾向量，
   于是该剔的没剔、不该剔的剔了

**修复**：剔除测试两侧必须同一坐标系——用世界系面心：
`dot(normal, eye - verts.mean(axis=0))`。

**教训**：z-buffer 让绘制顺序无关紧要，容易让人忘了剔除测试仍然是一段几何判断，
它的两个操作数必须同系。凡是"部分面消失、边缘斜切、拖着尖角"的渲染，
第一嫌疑就是剔除/投影的坐标系不一致。

## 2. 头灯式光照把白牙画成灰

**症状**：嘴里的白牙、脸上的眼白渲染出来是中灰色，整张贴图的明暗设计全部失效；
从某些角度看整个模型像蒙了一层灰。

**根因**：渲染器用了"随相机方向的头灯 + 环境项"。像素画的明暗**全部在贴图里**
（白牙 246,243,229 对近黑的口腔 58,14,26），任何把所有面拉向同一亮度的光照都会毁掉这层对比。
另外最初的环境项太低（0.52），朝 -Z 的面（嘴的开口方向）全部落到环境亮度。

**修复**：改用 MC 方块自己的面光照——顶 1.0 / 南北 0.8 / 东西 0.6 / 底 0.5，
倾斜面按法线分量平方加权混合（45° 斜面自然得到 0.8 一类的中间值）。
这样正交面精确落在游戏里的数值上，白色保持白色，深度感由**贴图**负责。

**教训**：做像素画渲染器时，光照的作用是"复现游戏的面系数"，不是"重新打光"。

## 3. 花瓣环半径小于被环绕体 —— 一团碎纸

**症状**：8 片花瓣围在花头四周，渲染出来不是花，是贴在方块侧面的一堆碎红色纸片。

**根因**：花瓣环起始半径 2，花头半宽 5——花瓣内段(半径 2→5)整个插在头部体积里，
只有露出头外的部分可见，且各片互相穿插。

**修复**：把整圈花瓣**下移到花头下方**（y 14-15，花头从 16 开始），半径从 2.5 起步、
长 6——起点藏在头底之下本来就不可见，露出的部分从轮廓外展开；再垫一圈绿色萼片
（更低、更平、相位错开 22.5°）补层次。

**教训**：环绕件的"起始半径"是相对**被环绕体的轮廓**而言的，不是相对轴心。
拿不准就把环放到被环绕体的高度范围之外。

## 4. 大长方体读作箱子

**症状**：花头是 10×8×10 的方块开一个方口，渲染出来像"开了一个门的箱子"，
不像生物的头。

**修复**：把 skull 拆成两层——下层 10×8，上层 8×6 四边各收 1 格叠上去，
脸（眼睛）画在收分后的上块正面。一眼从"箱子"变成"头"。
这是 MC 模型做圆润的标准手法：轮廓来自 1 格步进的阶梯，不来自圆滑曲面。

## 5. 亚像素特征：0.4 格的嘴缝是不存在的

**症状**：最初嘴的上下牙间隙 0.4 单位、牙缝 0.45 单位，渲染出来要么全糊要么是一条白带。

**修复**：所有"缝"做到 ≥1 格。嘴张开总高 4 格：下牙 1.5、暗带 1、上牙 1.5；
齿列之间留 1 格宽的暗缝，露出后面的喉咙和舌头——牙齿咬合感来自这些暗缝，不来自上下牙之间的缝。

**教训**：在 16px/block 的世界里先问"这是几像素"。小于 1 的尺寸要么放大，
要么换成"两个实体之间的暗缝"这种 1px 就能表达的结构。

## 6. UV 约定抄错来源 —— 渐变在南北面画反

**症状**（设计期发现，未进渲染）：花瓣"根暗尖亮"的渐变如果在南北面镜像，
半数花瓣的亮尖会朝向花头。

**根因**：minecraft-animation skill 的 Blender 导入器用"north/south 翻 u"的
box-net 约定（那是**它自己**的顶点排布约定，实测过与它的渲染一致）；Blockbench 本体
的显式 uv 却是 WYSIWYG（见 bbmodel-format.md §1-2）。两套都对，但**互不通用**，
照搬会把方向性渐变画反。对称画法（贴图沿中线左右对称）能掩盖差异，
方向性渐变（花瓣、叶片）则会暴露它。

**修复**：以 Blockbench 源码为准；up/down 面从相反方向看同一矩形的件
（沿 Z 放的叶片），干脆给两个矩形（`leaf_z_up` / `leaf_z_dn`），不做运行时翻转。

**教训**：约定类知识必须注明出处和适用范围。"某个 Blender 导入器验证过的表"
不等于"Blockbench 的约定"。

## 7. outliner 写平 —— 多个根 + 悬空引用

**症状**（结构期，由 validator 抓到）：把所有组平铺在 outliner 顶层、用 uuid 互相指，
Blockbench 会读成几个不相关的根，元素引用悬空。

**修复**：嵌套组**内联为对象**，只有元素用 uuid 字符串引用；
每个元素必须被 outliner 引用一次（validator 的"孤儿元素"检查）。
生成脚本里用 `walk(node)` 递归：先收集 `cubes` 的 uuid，再递归 `children`。

## 8. 读 Blockbench 源码：asar 与压缩 bundle

**症状**：直接 `grep` `resources/app.asar` 得到的是 vite 压缩后的单行 bundle，
变量名全是 `Ui`、`c`、`s`，读不了；而且 asar 头部按错误的偏移解析会直接 JSONDecodeError。

**修复**：

- asar 头：`@0=4`、`@4=headerSize`、`@8=headerSize-4`、`@12=jsonLen`、JSON 在 `@16`，
  文件数据从 `8+headerSize` 开始
- 要读的是 `dist/bundle.js.map`（约 19MB）：`sources[]` 是原始路径、
  `sourcesContent[]` 是未压缩源码，按路径下标取
- 只需要 5 个文件：`three_custom.js`（顶点序）、`cube.js`（updateUV / box-uv net）、
  `preview.ts`（默认相机）、`generic.ts`（free 格式）、`io/format.ts`（默认值）

**教训**：Electron 应用的"文档"经常就是它自己的 source map。格式问题先去那里找，
比试错快得多。

## 9. 环境类小坑（各耗掉一次构建）

- **Git Bash 的 `/tmp` 对原生 Windows Python 不成立**：内联脚本里写
  `open('/tmp/x.png','w')` 报 FileNotFoundError，但命令行参数里的 `/tmp/x.png`
  又会被 MSYS 改写成功。统一用 `os.environ['TEMP']` 或显式 `C:/` 路径
- **参考图全网不可达**：fandom 404/超时、萌娘 404、百度百科 403、必应跳 cn 站无结果。
  美术参考要么按名称+题材惯例自己设计并**显式声明假设**，要么一开始就找用户要图——
  不要把回合烧在重试 URL 上
- **asar 解析别照抄记忆里的偏移**：第一版把 jsonLen 读在 @8，直接把文件数据当 JSON 解析

## 10. 渲染器实现细节（各耗掉一次构建，记录备查）

- 三角形顶点是 `(x, y, inv_w)` 三元组，解包时 `x0, y0 = points[0]` 会崩——用 `points[0][:2]`
- 阴影遮罩和深度填充共用一个光栅函数时，`window`/`depth` 这类参数在遮罩路径里是 None，
  判空要在使用之前，不能先 `mask[...]` 再判
- 透视校正插值：屏幕空间重心坐标 λ 配每顶点 `1/w`，
  属性 = `Σ(λᵢ·aᵢ/wᵢ) / Σ(λᵢ/wᵢ)`；深度测试直接用插值出的 `1/w`（越大越近）
- 投影时把 `depth = -z_view` clamp 到 `1e-6` 防除零，但别让任何顶点真的落到相机背后
  ——那会把整个三角形拉成横跨全屏的垃圾

## 11. 逐面 UV 角的三元写反 —— 每个面的贴图 180° 旋转

**症状**：预览图里每个面的贴图都是"上下颠倒 + 左右镜像"。**噪点/迷彩贴图完全看不出来**（噪点
转 180° 还是噪点），只有方向性贴图能看出来——肌肉苦力怕的脸（眼在上、嘴在下）一眼就穿帮。
`bbmodel` 工程本身从未受影响，只有离线预览 PNG 错。

**根因**：渲染器把 uv 矩形四角配到面四个顶点时，三元表达式写反了：

```python
((u1 if cx else u2), (v1 if cy else v2))   # ✗ v0 拿到右下角 = 整面转 180°
((u2 if cx else u1), (v2 if cy else v1))   # ✓ v0 拿到左上角 (u1,v1)
```

两者只差一个 `if/else` 的取向，行文上几乎读不出差别——**源码推导是对的，代码写反了**，
而当时用于检查的模型（花盆、盆栽）贴图都是近似对称/噪点，没暴露出来。

**怎么定论**（这套办法值得复用）：

1. 用同一模型、同一相机，把两种映射各渲染一张，直接看图——苦力怕的脸一张正立、一张倒立；
2. 外部参照：`muscle_creeper_blockbench.png` 是 Blockbench GUI 的实机截屏，脸部朝向可作为真值；
3. 更普适的真值：**香草皮肤布局的脸本来就该正立**（`64×32` 皮肤里头部正面在 `(8,8)-(16,16)`），
   任何让脸倒过来的映射都是错的。

**教训**：UV 方向**不要用噪点贴图验证**。用一个"脸/字母/箭头"测试贴图，或者在模型上找一块
有明确上下之分的贴图；把这张方向性贴图作为预览器的固定自检用例。

## 12. Blockbench 保存过的工程是 5.0 格式 —— 组的旋转会"失效"

**症状**：`ship_in_bottle.bbmodel` 在 Blockbench 里被打开保存过之后，渲染/解析脚本按老办法
从 outliner 读组的 `origin`/`rotation`，结果全部读成缺省值。

**根因**：Blockbench 5.x 保存工程时写 `meta.format_version = "5.0"`，把组整个搬到顶层
`groups` 数组（name/origin/rotation/children 都在那里），`outliner` 里的节点退化成
`{uuid, isOpen, children}` 纯引用；元素还多出 `scope`/`autouv`/`locked` 等字段，数字按整数写。
详见 [bbmodel-format.md §11](bbmodel-format.md)。

**为什么一开始没炸**：组的 `origin` 只是 pivot，**不会平移子元素**（元素的 from/to 是模型空间的
绝对坐标），而那个工程里 7 个组的 `rotation` 全是 0 —— 于是"读不到"和"读到 0"结果一样。
**一旦有旋转组（摆动、倾斜）就会静默渲染错**。

**修复**：解析时两边都读——节点里没有 `origin`/`rotation` 就按 `uuid` 查顶层 `groups` 表。
已落进 `tools/preview_bbmodel.py` 的 `collect_quads`，并用"给 `hull` 组注入 45° 旋转后画面必须变化"
的对照实验验证（4.5 内联组同样对照，作为回归）。

**顺带确认的事**：4.5 → 5.0 重新保存**不改几何**——同一渲染器对两个版本输出逐像素一致
（平均差 0.000）。但生成脚本只会写 4.5，对 Blockbench 保存过的文件重跑脚本会退回 4.5 并丢掉 GUI 修改。

## 13. 镜像函数把旋转轴心整个取负 —— 左右两边一个贴合一个悬空（鸟居，2026-09-25）

**症状**：鸟居的笠木端段和拟宝珠用 `mirror_x` 从东侧复制西侧，渲染出来**东侧金顶稳稳嵌进上翘的
梁端、西侧同样造型的金顶却悬在半空**——而且模型是精确镜像、相机是正对称的，渲染结果却不对称。
更早的一版里西侧笠木端段干脆"消失"（正面图里看不出任何异常）。

**定位**：
1. 先怀疑自己的目测：写脚本从 bbmodel 反解每个方块的**世界 AABB**（用与渲染器同一套
   `node_matrix` 组变变换）——`kasagi_west` 的 AABB 是 x −6.28..−0.66，正确位置应是
   −16.16..−10.54：整段转飞了 10 个单位，恰好**整个藏进 kasagi_main 的体积里**，所以正面图"看不出"；
2. 手算复核：绕 (−11, −35.5) 转 −8° 正好复现观测 AABB —— **轴心的 y 被翻成了负值**。
   `mirror_x` 里写的是 `tuple(-v for v in origin)`，把 (11, 35.5, 0) 镜成了 (−11, **−35.5**, 0)。
   跨 x=0 平面的镜像只把 **x 分量**变号，y/z 不动；
3. 为什么西柱没暴露：柱脚轴心 (11, 3, 0) 被翻成 (−11, −3, 0) 后误差只有 ~0.5 单位
   （轴心离方块近、方块又高），歪打正着地看不出来——**同一个 bug 在不同几何上症状天差地别**。

**修复**：`origin` 只翻 x：`(-ox, oy, oz)`；旋转的翻号规则不变（跨 x 镜像：rx→−rx、ry 不变、rz→−rz）。
修完用"每对 east/west 方块的世界 AABB 必须满足 x 和恰好为 0、y/z 相等"做了全模型对称性断言。

**教训**：
- 镜像/对称类变换函数，**测试不能只看"有没有这个东西"**，要断言数值（这里是对称不变量）；
  "渲染出来差不多"在轴心类 bug 面前毫无分辨力；
- "消失的件"先查它是不是**藏进了别的件的体积里**（AABB 一算便知），而不是先怀疑渲染器剔除了它；
- 对称模型 + 对称相机渲染出不对称，**必然是数据不对称**——这时直接数值对比左右两半，
  不要在图上做像素考古。

## 14. 旋转件的 from/to 与 origin 写在两个坐标系 —— 斜板整车乱飞（M1A2，2026-09-25）

**症状**：第一版 M1A2 的预览里，首上装甲板翘在车体上空、下首板垂到车底下、
两块炮塔颊板立在车尾——三处旋转件全部甩到离预期位置几十格的地方，而车体、炮塔主体
（不旋转的件）完全正常。同一个构建里 validator 还抓到左侧全部镜像件
`from.x > to.x`（负 extent）。

**根因**（两个，都出在"坐标空间"上）：

1. **旋转件的 `from`/`to` 与 `origin` 不在同一处**。花瓣脚本里花瓣的 from/to 就贴着
   origin（origin 在花瓣根部边缘），照着"套公式"写坦克时却把 from/to 写在
   "未旋转时的大致区域"（模型中部，z −23..0），origin 却写在几十格外的铰链
   （z −52）——旋转以远处的点为轴，把整块板甩飞。几何直觉里"板在那儿、轴在那儿"是
   两个独立参数，但 bbmodel 里**元素坐标本身就是未旋转姿态的绝对坐标**，
   "先摆好未旋转姿态、origin 放在姿态里的铰链上"才是一致的写法。
2. **镜像盒子把 from 的 x 也直接取负**：左侧件 `(mx(27.5), y, z)..(mx(30), y, z)`
   变成 `−27.5..−30`，from > to，六个面的顶点序全部反向（法线朝内）。
   跨 x=0 镜像一个盒子要**交换两端**：`from' = (−to_x, from_y, from_z)`、
   `to' = (−from_x, to_y, to_z)`——和坑 13 的"轴心只翻 x"是姊妹坑，
   都是"镜像 = 逐分量取负"这个直觉在起作用。

**修复**：

1. 统一为"悬挂在铰链上再旋转"：竖直板挂在铰链 H（板长 = 目标弦长 |H−T|，
   厚度居中于铰链平面），origin 设 H，Rx(θ) 的下端落点是
   `(Δy, Δz) = (−L·cosθ, −L·sinθ)`，反解 `θ = atan2(−Δz, −Δy)`
   （首上板落到 (10, −63.5) → θ=30°；下首板 → θ=−52.4°）；
   炮塔颊板从炮塔尖沿 +z 摆出、`ry = atan2(Δx, Δz)`（=55.4°）。
   修完先手算端点落点，再渲染侧视/正视确认；
2. 加 `xbox(s, frm, to)`：镜像时交换两端，保证 from ≤ to。
   修完 validator 全绿。

**教训**：
- **元素的 from/to 永远是"未旋转姿态"的坐标**；旋转件的写法是
  "摆未旋转姿态（贴着铰链）+ origin 在铰链 + 旋转角"，不是"把目标姿态当坐标 + 远处设轴心"。
  从别的脚本"照着写"时，要先确认人家的坐标和轴心是什么空间关系，不能只看形似；
- 镜像函数的又一种死法（坑 13 是轴心被逐分量取负，这里是盒子坐标取负不换端）。
  镜像写完必须过 validator 的负 extent 检查 + 左右 AABB 对称断言，
  "预览看着差不多"完全无法分辨"恰好没错"和"错得对称"；

# 坑与修复（第二轮，2026-09-25：荷枪实弹的美军士兵）

这一轮的题目第一次同时用到**组旋转、姿态求解、武器挂手**，也因此第一次踩到"结构自检"
能抓、肉眼看图很难抓的坑。按发现顺序排列，定位过程保留。

## 13. 组的仿射链推错一层 —— 拳心离目标 0.47 / 1.35 单位

**症状**：`verify_pose()` 报 `right_fist on target err 4.68e-01`、`left_fist … 1.35e+00`，
但"卡宾枪滚转"一项误差 1e-16（精确）。也就是说旋转全对、位置差半格——手没落在枪上。

**定位**：旋转对而平移错 ⇒ 问题在链的**平移分量**。写校验函数时我把每个节点的变换
记成 `(R_i, origin_i)` 然后算 `R @ (p - origin) + origin`——这只对**单层**成立：
多层复合时每层都贡献一个 `(I - R_i)·o_i`，而且会被**更深层的父旋转**继续搬运。
正确形式是沿树下推 `R' = R @ R_local`、`t' = t + R @ (I - R_local) @ o`
（父在左！写成 `R_local @ R` 会在两层以上转反）。

**修复**：`walk_groups()` 直接返回 `(R, t)` 并断言 `R @ p + t`；同一份实现留在
`tools/bbmodel_kit.py` 里，预览器、校验器、生成脚本三方共用一套代数。

**教训**：把"我推导的变换"和"Blockbench 的变换"当成两个独立的东西，**必须有一处断言把它们对起来**。
本轮选了四个可断言量：两个拳心、枪口位置、枪身"上"方向。前三个量级差半格就说明公式错了。

## 14. 挂在手下的武器：局部偏移要不要再乘一次组旋转

**症状**：拳心误差修好后，枪口位置仍差 **20.0 单位**（正好是枪长量级），滚转仍精确。
渲染图会看到枪绕着握把转了一个大角度。

**根因**：我先把枪的局部偏移 `L` 乘上 `R_local` 再写进方块座标
（`p_authored = pivot + R_local·L`）。但组旋转本身已经会作用一次：
`p_world = G + R_chain · (T_g(p) - pivot)`，而 `T_g(p) - pivot = R_local·(p_authored - pivot)`。
要让 `p_world = G + R_world·L`，需要 `R_chain·R_local·(p_authored - pivot) = R_world·L`，
即 `p_authored = pivot + L`（**偏移原样**），组旋转取 `R_local = R_chain⁻¹·R_world`。
多乘的那一次 `R_local` 让结果变成 `G + R_world·R_local·L`。

**教训**：**"枢轴在原点、几何绕枢轴转、再被父链搬走"——三件事各作用一次，别重复施加。**
推导完之后一定要用第 13 条那套断言回来验一遍；两个坑（13、14）症状相似但一个是平移一个是旋转，
分开断言就能一眼区分。

## 15. 共面同向面（z-fighting）—— 眼睛看不出，检查器看得出

**症状**：无。渲染图上看不出任何问题。
**但检查器报了 42 处**"两个面共面、朝向相同、面积重叠"，其中至少三处是真 bug：

- **左大腿口袋跑到右腿上**：口袋座标写成 `bx(-1, -4.75, -4.25, …)`，
  而 `bx(sx, …)` 的设计是"传右手座标、内部乘 sx"。负座标被乘了两次 -1 ⇒ 口袋出现在 +X 侧，
  正好和右腿的枪套重叠（检查器报 `holster / cargo_pocket on x=4.250`）。渲染图上是"枪套旁边多了块布"，肉眼极易归因成"枪套画得怪"。
- **两条裤腿的束口/鞋底在中线互压**：右腿束口 `-0.25..4.75`、左腿 `-4.75..0.25` 在中线重叠 0.5，
  两面的 `z=-3` 平面完全重合。修法是**把腿拉开**（`|x| 0.75..4.75`，中线留 1.5 的缝），
  这样两侧束口都能"两侧各鼓 0.5"而不互相压面。
- **盔顶与头顶共面**：头盔壳 `y 29..32` 与头 `y 24..32` 的顶面同在 `y=32`。
  修法是让壳比头**高出一点**（`29..32.4`），而不是靠"材质不同所以看不出"。

**为什么要写这个检查**：z-fighting 是**渲染期**的 tie，贴图/几何数据完全合法，
validator 也不查；而它在静态预览图里经常只表现为"某处颜色略花"，会被当成贴图问题。
判定条件很便宜：两个面在同一平面、法线同向、二维投影面积重叠 > ε。
**反向共面（背靠背）是合法的、而且我们故意大量使用**（贴片贴在袖子上、枪管插进机匣），
所以检查器必须按"同向"过滤，否则满屏误报。

## 16. 姿态后的接触要按姿态后的盒子算

**症状**：共面检查器在"复位姿态"（authored frame）下报了 20 处，看起来像一堆穿模，
但渲染图完全正常——因为那些件（手、前臂、枪）**渲染时并不在复位姿态**。

**修复**：检查器分两档：
- 同一链条内的方块、或两边都不带旋转的方块 → 在复位坐标系里严格判共面（刚性变换保共面、保面积）；
- 至少一侧在旋转链里 → 不算共面，改算**姿态后的 AABB 接触体积**，作为"需要人眼过一遍"的清单。

**教训**：结构检查必须明确"在哪个坐标系里成立"。渲染的是姿态后的盒子，
所以任何"会不会穿模/会不会打架"的判断，都要在姿态后做；复位坐标只对不受旋转影响的件有效。

## 17. `round(0.5) == 0`：0.5 单位厚的盒子生成 0 像素的 uv 矩形

**症状**：`paint_pouch` 抛 `IndexError: index 1 is out of bounds for axis 0 with size 1`。
**根因**：口袋厚 0.5 单位 → `face_size` 用 `int(round(0.5))`，而 Python 的 round 是
**银行家舍入**（.5 进偶数）⇒ 0。uv 矩形 `[x, x+0]` 宽 0 像素，画笔一写就越界。
**修复**：`face_size` 统一 `max(1, round(...))`；同时把该件加厚到 1 单位。
**教训**：贴图尺寸是**整数像素**，任何"往下取整"的地方都要有下限保护；
另外 `<1 单位` 的件本来就不该存在（见 SKILL.md 规则 2），0.5 是在报警而不是在提醒。

## 18. 深色盔罩 vs 浅色迷彩盔：帽子与头盔的分界

**症状**：头盔反复渲染成"宽檐帽/渔夫帽"，改了四次都不是形状问题：
先削宽度（10 → 9）、再去掉三段式阶梯、再去掉一圈 3D 盔带（改成贴图上画）、
最后把盔压低到眉线——**仍然是帽子**。

**定位**：把头部单独放大渲染（`--distance 24 --target 0 29 0`）逐张比对，才看清三件事叠加：
1. 盔体比头只宽 0.5，形状其实没错；
2. 但"**浅迷彩盔体 + 一圈深色带**"在视觉上就是帽檐 + 帽带：带子一圈把盔分成上下两截；
3. 更关键的是**明度**：盔和制服、脸、背景的明度都接近，读不出"硬壳"这个材质。

**修复**：把盔罩整体压成**暗色**（`HELM` 色阶，基色 100,98,78 对制服的 186,168,132），
只保留一圈很淡的下缘暗边，不再画带、不加 3D 唇边；另外把后颈加长片做出来（`y 26.5..29`），
让侧影有"前高后低"的盔形。一改就对了。

**教训**：**"像什么"首先是明度分层问题，其次才是轮廓问题。** 在 1 px = 1 单位的像素画里，
浅色物压浅色物必然读成同一坨；MC 的官方盔（铁/钻/下界合金）也是靠**材质色**一眼区分头盔的。
轮廓该削的当然还要削，但先解决明度。

## 19. 镜子：把"右肩的件"复制到左边时的两种错法

**症状**：本轮右臂的国旗臂章、左臂的部队臂章、左右腿的枪套/口袋，一共 6 件镜像件，
代码里用一个 `bx(sx, x0, x1, …)` 统一处理（`sx = ±1`，传右手座标）。
出现了两种错法：**负座标被二次取反**（第 15 条的口袋）、
**"两侧各鼓 0.5"的件在中线互压**（第 15 条的束口）。

**修复/约定**：镜像件一律"**只用正座标描述右件**"，`bx()` 负责取反；
中线附近的加宽要么只向外鼓、要么先把两侧主体拉开。
**教训**：镜像是对称件最容易出错的地方，而错误结果看起来往往"很合理"——
**让检查器替你数**（共面 + AABB 接触两份清单），比逐件盯图靠谱。
